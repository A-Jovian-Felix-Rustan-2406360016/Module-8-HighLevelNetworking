Reflection : 
1. Dari ketiga tersebut, perbedaan utamanya terletak di pola komunikasinya. Masing-masing memiliki karakteristik tersendiri yang cocok digunakan di kondisi atau situasi tertentu. Berikut penjelasan detail masing-masing : 
- Unary : Ini adalah pola komunikasi yang paling sederhana karena satu request akan memiliki satu response. Karena sifatnya ini, ia cocok digunakan pada operasi tunggal, sederhana, dan cepat seperti pada PaymentService yang kita implementasi dalam tutorial ini.
- Server Streaming : Ini bersifat satu request membutuhkan banyak response (aliran data) secara bertahap. Biasanya cocok untuk mengambil kumpulan data besar seperti mengambil riwayat transaksi dari TransactionService yang sudah diimplementasi dari tutorial ini.
- Bi-directional Streaming : Jenis pola ini terlihat dari client dan server dapat saling mengirim data terus-menerus secara bersamaan dan bersifat asinkronus. Oleh karena itu, jenis ini cocok digunakan untuk aplikasi interaktif. Salah satu contohnya yaitu implementasi ChatService pada tutorial ini. 

2. Security gRPC di rust memiliki beberapa pertimbangan terkait autentikasi, otorisasi, dan enkripsi data. Untuk autentikasi dan otorisasi, di rust khususnya tonic, hal ini ditangani menggunakan interceptors dimana kita dapat memeriksa metadata dari setiap permintaan untuk memvalidasi token seperti JWT (JSON Web Token) sebelum diteruskan ke bisnis logika. Sedangkan untuk enkripsi, kita wajib menggunakan TLS (Transport Layer Security) yang juga didukung oleh tonic untuk mengenkripsi aliran data agar aman dari penyadapan. Selain itu, kita juga membutuhkan beberapa tambahan seperti rate liming, input validation, dan audit logging untuk memberikan lapisan tambahan sehingga keamanan secara keseluruhan terjaga.

3. Tantangan utama saat mengelola bidirectional streaming adalah terkait manajemen concurrency dan state karena rawan terjadinya race condition dan resource leak. Pada aplikasi chat, server harus melacak siapa saja client yang sedang terhubung dan mengelola rute pesan ke pengguna yang tepat. Jika misalnya client tiba-tiba disconnect, apakah stream berhenti bersih? Selain itu, kita juga harus memperhatikan pada penanganan backpressure yaitu memastikan server tidak kehabisan memori ketika pengiriman pesan lebih cepat daripada penerimaan. Error handling di sini juga lebih kompleks karena berjalan dua arah secara paralel sehingga debuggingnya lebih ribet dibanding yang lainnya.

4. Penggunaan tokio_stream::wrappers::ReceiverStream memiliki kelebihan dan kekurangannya masing-masing :
- Kelebihan : Bersifat praktis dan memudahkan kita untuk langsung convert channel mpsc (Multi Producer, Single Customer) standar dari Tokio menjadi tipe data Stream yang diwajibkan oleh gRPC.
- Kekurangan : Ada sedikit overhead dalam pengiriman melalui channel. Selain itu, jika batas buffer channel penuh dan tidak dikelola dengan baik, maka proses pengiriman data bisa terblokir atau pesan dapat hilang jika terjadi kegagalan.

5. Struktur kode bisa lebih modular dengan menghindari menaruh semua implementasi di satu tempat (file). Kita bisa memisahkan menjadi beberapa layer seperti transport (gRPC), service logic, dan domain logic. Kita juga bisa gunakan trait untuk abstraction, dependency injection untuk service, dan pisahkan protobuf dari business logic sehingga code lebih mudah di maintain dan reuse.

6. Payment Processing di dunia nyata jauh lebih kompleks dari yang sudah kita implementasikan dari tutorial ini sehingga membutuhkan step tambahan untuk handle logika yang lebih kompleks. Di kasus nyata, kita membutuhkan komunikasi dengan pihak ketiga (Payment Gateway), pencatatan transaksi ke database, penanganan idempotency key untuk mencegah double charge jika ada retry jaringan, serta sistem logging dan tracing sehingga kita dapat menelusuri jika pembayaran gagal. Lalu, kita juga perlu menambahkan berbagai lapisan security karena proses payment bisa dianggap sebagai sesuatu yang penting.

7. Dengan menggunakan gRPC, hal ini membuat arsitektur lebih contract-driven karena memakai protobuf sebagai kontrak komunikasi yang kuat. Ini bagus untuk konsistensi antar service tetapi bikin sistem lebih strict. Dari sisi lain, interoperability menjadi kuat antar bahasa sehingga integrasi layanan lebih stabil (misalnya server rust berbicara dengan Go) tetapi untuk browser client menjadi lebih ribet karena gRPC tidak native di HTTP/1 sehingga terkadang butuh gateway tambahan. 

8. Keuntungan dan kerugian HTTP/2 dibanding HTTP/1.1 :
- Keuntungan : HTTP/2 memiliki fitur multiplexing dimana bisa mengirim banyak permintaan secara paralel di satu koneksi TCP. Selain itu, ia juga punya kompresi header dan format pengiriman biner yang jauh lebih cepat dan ringan dibanding teks biasa.
- Kerugian : Format biner sulit dibaca secara langsung oleh manusia sehingga proses debugging jaringan dapat lebih sulit dibanding HTTP/1.1 yang menggunakan teks biasa. 

9. Dari segi responsiveness, REST API memang tidak dirancang untuk real time karena bersifat stateless sehingga setiap interaksi harus mulai dari nol. Untuk bisa mencapai real time, REST harus menggunakan teknik lain seperti polling atau meningkatkan koneksi ke WebSocket yang penanganannya terpisah. Sebaliknya, bidirectional streaming gRPC secara alami memang jauh lebih responsif karena sudah berjalan di satu koneksi HTTP/2 yang cepat dan koneksi tetap terbuka sehingga memiliki latensi rendah tanpa perlu buka tutup koneksi HTTP.

10. Schema-based (protobuf) membuat komunikasi lebih cepat dan didalamnya ada type safe sehingga mencegah banyak kesalahan runtime karena salah tipe data. Namun, schema-based ini kurang fleksibel, kalau schema berubah, harus update semua pihak. Sedangkan JSON di REST lebih fleksibel dan mudah debugging tetapi lebih berat dan rawan error karena tidak ada strict typing.
